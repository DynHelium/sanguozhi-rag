# 评测

两部分：检索评测不经过大模型，看检索器能不能把答案所在的段落排到前面；回答评测看给模型资料、让它自己查，对回答的事实正确率有多大帮助。

## 检索

题目：`eval/retrieval.jsonl`，48 道标了 gold 段落（源 id）的题，另有 1 道原文没有答案。hit@k：答案所在的块是否在前 k 名。
宽松口径把挂在答案段落上的裴注也算命中，严格口径只算答案段落本身。

| 检索方式 | hit@1 | hit@5 | hit@10 | MRR |
|---|---|---|---|---|
| BM25，搜原文 | 0.25 / 0.23 | 0.31 / 0.29 | 0.40 / 0.35 | 0.28 / 0.26 |
| BM25 + 向量（RRF） | 0.31 / 0.27 | 0.54 / 0.50 | 0.65 / 0.60 | 0.42 / 0.38 |
| + 别名扩展 | 0.31 / 0.27 | 0.60 / 0.56 | 0.69 / 0.65 | 0.43 / 0.39 |
| 搜白话：BM25 | 0.40 / 0.40 | 0.60 / 0.56 | 0.62 / 0.58 | 0.49 / 0.46 |
| 搜白话：BM25 + 向量 + 别名扩展（agent 用的） | 0.52 / 0.48 | 0.67 / 0.62 | 0.81 / 0.75 | 0.59 / 0.54 |

（宽松 / 严格。）难点是白话提问对文言原文：问"曹操因为什么逃离洛阳"，原文写的是"太祖"，BM25 找不到；白话译文的用词和
纪年写法接近提问（"薨"→"去世"，"七年"→"建安七年"），所以搜白话好得多；同一个人的不同称呼（太祖、曹公、魏武）由别名扩展处理。
查询端的停用词是照着这 48 道题挑的，所以它们算开发集。

37 道留出题（`eval/questions-holdout.jsonl` 里有 gold 的部分）上，搜原文的 BM25 hit@10 为 0.78，agent 用的检索为 0.97
（MRR 0.62 → 0.91）。直接用英文问题检索（`eval/questions-en.jsonl`，100 道有 gold）hit@10 只有 0.39：索引是中文的，所以 agent
会先把人名和术语译回中文再搜。

```bash
uv run python -m eval.run_retrieval -r bm25
uv run python -m eval.run_retrieval -r hybrid --index trans --alias route2   # 加 --strict 看严格口径
```

## 回答：检索带来多少帮助

### 设计

**题目**：50 道（`eval/questions-rag50.jsonl`，英文版 `eval/questions-rag50-en.jsonl`）。其中 38 道出自作者：推断、演义辨析、
官职地理各 10 道，以及 8 道按人平时的问法提的开放题；另外 12 道按固定种子从留出题、事实题、人物题里随机抽取。每题中英文各问一次。
这些题在开发过程中用过，所以检索和 agent 的数字可能偏乐观。

**五组**，每个模型都跑这五组，每组每题一遍：

| 组 | 资料 | 工具 | prompt | 代码介入 |
|---|---|---|---|---|
| 闭卷 | 无 | 无 | 最小 prompt | 无 |
| 检索一次 | 用问题检索一次，前 10 组放进用户消息 | 无 | 最小 prompt | 无 |
| gold 原文 | gold 段落所在的块放进用户消息 | 无 | 最小 prompt | 无 |
| 只给工具 | 自己查 | search / read / who / era | 最小 prompt + 一句"可以调用工具" | 无 |
| 网页配置 | 自己查 | 同上 | 网页聊天用的完整 prompt | 网页聊天的全部介入 |

- **最小 prompt**（前四组共用，两个模型相同）：以《三国志》为准回答；直接陈述事实，不确定的年份、人名、数字说不确定；
  中文提问用中文答，英文提问用英文答。不要求引原文，也不要求标编号。
- **控制住的**：前四组之间只差给模型什么资料。工具说明只写功能，不写搜法；工具用完时的提示是中性的"请直接回答"；
  四组都不自查、不改引文；截断或空回答时都重答一次；输出上限都是 16384 token；同一模型各组的思考档相同
  （DeepSeek low，Haiku medium）。
- **网页配置**：和网页聊天（`app/chat.py`）相同的 prompt、工具和代码介入（`eval/run_rag.py --group production`；输出上限沿用网页的 8192 token，不接游戏的处理函数）。它的 prompt 要求事实只来自查到的原文、
  引原文并标编号，代码介入包括搜得少时提示再查、汇总题提示、"没找到"时核实、自查、引文修正、编号修正、语言检查。所以它和
  前四组之间不止差一个条件，这一行回答的是"网页上的系统比裸模型好多少"。

模型：DeepSeek V4.1 Flash（经 OpenRouter）和 Claude Haiku 5.5（Claude 原生接口）。

### 判卷

判卷只看回答陈述的事实对不对，不看写法、详略，也不看有没有引原文。

- **事实清单**（`eval/checklists-rag50.jsonl`）：每题在跑题之前写好（判卷后改过一次标注，见下面"清单的修改"），列出要答到的要点（标出核心项和题目明确要求的项）
  和常见的错误说法（混淆、演义当正史、同名的另一个人）。评委对每份回答逐项标"答到 / 没提到 / 说错 / 只说不确定"。
- **判定由代码按规则算**（`eval/judge_v2.py`）：
  - **错**：核心项没答到或说错，或者出现了清单列出的错误说法。例外：题目自带判法写了"只答到 X 算部分对"的三题（i-02、f-22、p-01），
    标了 `core_partial` 的核心项只是没答到时算部分，说错仍算错；
  - **部分**：核心项都对，但题目明确要求的其他项漏了或错了；背景细节写错了；或者回答里有编造的史料（说成史书原文或史书记载、
    但原文里找不到或不符的引文和说法），或有和原文矛盾的事实；
  - **对**：其余。题目没问的背景细节没写，不扣分。
- **评委**：Claude Sonnet，按 `eval/judge_prompt_v2.md` 判，可以用 `eval.find` 检索原文核对。同一题同一语言的五组回答放进一个包，
  打包前统一格式（去掉 `[n]` 编号，引号换成同一种），标签随机。回答的详略和用词仍能看出是否查过资料，所以这不是严格的盲判；
  逐项清单加上代码算判定，用来减少评委的自由裁量。
- **清单的修改**：第一轮判卷后，作者发现有些清单项是题目没问的背景细节，回答没写也被扣分，于是给每项标注"题目要求 / 背景细节"，
  并要求逐条核对说成史书记载的内容，然后全部重判。每次改动和理由记在 `eval/checklists-rag50.changes.md`。
- 评委标为拿不准的条目（DeepSeek 12 条，Haiku 24 条）按评委的最佳判断计入。

### 怎么读

- **Haiku 自己知道得少，资料的帮助很大**：闭卷时中英文各错 15 题，编造多集中在闭卷。给它资料（任何一种方式）都大幅提高正确率。
- **DeepSeek 自己知道得多**：闭卷就有 41 / 43 题完全正确。只给工具相对闭卷看不出差别（区间含 0），网页配置才显著更好，
  而且比只给工具也显著更好。对 DeepSeek 起作用的是网页配置的 prompt 和代码介入（两者没有拆开测），而不是工具本身。
- **只给工具时，模型偶尔不查就答**：100 题里 DeepSeek 有 5 题、Haiku 有 9 题一次工具都没调；网页配置里每题都查了。
- **用英文问题检索一次帮助不大**（DeepSeek −4，Haiku +10，区间都含 0）：索引是中文的，英文问题搜不到对应段落。agent 会先把人名和术语译成中文再搜。
- **gold 原文是上限，但不总是满分**：Haiku 英文题给了 gold 原文仍有 7 题只答对一部分，读懂文言、换算年代仍会出错。

### 局限

- 50 题、每组一遍，置信区间较宽；5 个百分点左右的差别看不出来。
- 评委只有一个（Claude Sonnet），和 Haiku 是同一家的模型。
- 题目在开发过程中用过，检索和 agent 组的结果可能偏乐观。

### 复现

```bash
# 跑题: 每组一次, 每个题集一次 (Haiku: 环境变量 LLM_BACKEND=anthropic)
uv run python -m eval.run_rag --group closed --models deepseek-v4.1-flash --effort low \
    --questions eval/questions-rag50.jsonl --name rag-ds-closed-rag50
# --group 可选 closed / static / oracle / agentic / production
```

判卷工具（打包、按清单算判定）、事实清单和逐题的回答与判决在 [`eval-judging`](https://github.com/DynHelium/sanguozhi-rag/tree/eval-judging) 分支：

```bash
uv run python -m eval.judge_v2 prep rag-ds     # 五组回答打包, 统一格式, 随机标签
# (判卷 agent 按 eval/judge_prompt_v2.md 逐包判)
uv run python -m eval.judge_v2 merge rag-ds    # 按清单算判定, 还原到各组
```
